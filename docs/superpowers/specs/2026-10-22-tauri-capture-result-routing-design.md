# Tauri Capture Result Routing

## Goal

Route every completed still capture from the existing Rust capture engine into
the Tauri image editor. Area, window, full desktop and scrolling capture must
all open the Tauri editor, whether started from the launcher, tray or a global
hotkey. Video keeps its current recording and preview workflow.

This closes the missing integration in the approved Tauri editor design. It
does not replace the capture engine or reimplement capture in JavaScript.

## Root Cause

The installed Tauri launcher and editor are current, but the capture engine
still calls the native `present_project` path after producing a frame. The
Tauri editor can currently receive only a file chosen in its own webview. No
capture-result channel exists between the long-running capture engine and the
Tauri backend, so captures necessarily open the old Win32 editor.

## Considered Approaches

### Chosen: bounded event plus owned temporary image

The engine writes an atomic PNG into a Tauri-owned temporary directory and
writes one bounded JSON event to its stdout channel. The event contains an
opaque filename token and capture metadata, never an arbitrary path. A Tauri
reader validates and adopts the image, deletes the transfer, creates an editor
session and routes it to a tab or window.

This works for launcher commands and asynchronous global hotkeys, avoids binary
or base64 payloads in IPC and keeps capture latency low.

### Rejected: directory polling

Polling a result directory would be simpler, but it adds avoidable delay,
requires duplicate/stale-file rules and makes cancellation and engine failures
harder to distinguish from a slow capture.

### Rejected: reverse `WM_COPYDATA`

Sending a result token directly to a Tauri window would avoid stdout, but it
would couple result delivery to a particular HWND and require native message
subclassing in the webview host. It is less portable inside Tauri and more
fragile when editor windows are created or closed.

## Architecture

### Capture engine

Tauri starts the engine with `--tauri-engine` and a newly created, instance-
owned result directory. The directory is not supplied by JavaScript.

When a still capture completes in Tauri mode, the engine:

1. encodes the captured frame as PNG into a temporary file;
2. flushes and atomically renames it to its final opaque token filename;
3. emits one versioned JSON-line `capture_ready` event on stdout;
4. includes the saved open destination (`tab` or `window`) and capture kind;
5. does not call the native image-editor presentation path.

The engine keeps using the current native selection, target detection, scrolling
controller, Escape/Stop behavior and video workflow. A normal non-Tauri launch
continues to open the native editor exactly as before.

### Tauri backend

The backend owns the result directory and a dedicated stdout reader for the
capture child. It accepts only known event versions and token characters,
requires the resolved file to stay inside that directory, enforces the existing
image byte limit and deletes each transfer after successful adoption or a
terminal failure.

Each adopted image starts an independent Rust editor-service process. Sessions
are stored in a registry under generated session IDs rather than the current
single global editor slot. Editor commands include the session ID so Undo/Redo,
selection and previews cannot cross documents.

The registry is capped at 16 live image sessions, matching the native editor's
existing workspace limit. Closing a tab releases its service and temporary
directory. Closing the launcher performs the existing safe engine shutdown and
then releases all editor sessions.

### Tauri frontend and windows

The compact launcher remains available after a capture. Captures open in Tauri
editor windows:

- **New tab:** add and activate a tab in the most recently active editor window;
  create an editor window if none exists.
- **New window:** create a separate editor window containing the new document.

Each editor window receives only session descriptors assigned to that window.
The tab strip becomes functional: it switches sessions, displays a localized
capture name and closes only the chosen session. All canvas and toolbar commands
target the active session. A late result from an inactive capture creates the
requested destination without replacing another tab.

Editor windows use labels generated by Rust and are granted only the existing
core IPC capability. JavaScript cannot choose result paths, process IDs or
executable paths.

## Data Flow

1. A launcher button, tray command or registered hotkey starts a still capture.
2. Tauri windows hide while the existing native capture interface is active.
3. The engine completes or stops the capture and atomically writes the PNG.
4. The engine emits `capture_ready` with token, kind and destination.
5. The Tauri reader validates the token and image, creates an editor session and
   assigns it to the requested editor host.
6. The target webview receives a session-added event, activates the new tab and
   requests its Rust view model and preview.
7. The launcher is restored independently of editor loading.

Cancellation emits no capture result and opens no editor. Video result handling
does not use this channel in this phase.

## Failure Handling

- Malformed, oversized or unknown events are rejected and logged without
  opening a document.
- A token outside the owned directory is rejected before any read.
- A missing, oversized or invalid PNG produces one compact Tauri notice and the
  launcher remains usable.
- If an editor service cannot start, Tauri deletes the transfer and reports the
  failure without falling back silently to the old editor.
- If stdout closes unexpectedly, the backend marks the engine unavailable and
  the next launcher action may restart it using a fresh result directory.
- A capture-result failure never deletes a user file and never affects another
  editor session.

## Testing

Implementation follows test-first increments:

1. protocol tests reject invalid versions, event types, tokens and oversized
   messages;
2. engine tests prove Tauri mode emits a result and bypasses native presentation
   while normal mode keeps the native path;
3. backend tests prove path confinement, atomic adoption, cleanup, session
   isolation and the 16-session limit;
4. frontend tests prove tab switching, tab close, command session IDs and
   New-tab/New-window routing;
5. packaged Windows tests cover Area, Window, Desktop and Scrolling from the
   launcher plus at least one global hotkey, including Escape/Stop for scrolling;
6. regression tests cover native mode and video behavior.

Acceptance requires that a capture from the installed `0.15.0-alpha.1` package
opens the Tauri editor shown by the launcher design, not the Win32 editor, and
that two captures retain independent editable state.

## Out of Scope

- Migrating video preview or video editing into Tauri.
- Replacing native selection, scrolling detection or recording code.
- Changing the .NET SnapZy installation or shortcuts.
- Publishing a release or pushing commits.
- Completing unrelated editor placeholder commands in this integration change.
