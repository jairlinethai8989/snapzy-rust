# SnapZy Rust Preview 0.4.0-alpha.2 Verification

Date: 2026-10-09, Asia/Bangkok. Local portable Windows x64 scrolling-input
bugfix candidate. No installer, push, tag, release or .NET changes.

## Report And Investigation

The tester confirmed that manually rotating the wheel over the source table did
not scroll it, not merely that automatic scrolling was absent. This pilot still
has no automatic wheel input; the expected contract is to leave manual input
available in the original application.

The previous fixture changed table pixels directly and proved stitching, not
input handoff. New native checks inspect selection-overlay teardown, mouse
capture ownership, foreground target and the actual visible window under a
source-table point. Wheel messages are sent to that window; received deltas
drive the fixture offsets before exact PNG/clipboard assertions.

One foreground check failed against the original behavior:
`artifacts/smoke-a70086b0387f49f493ca782b55bb46bf`. A diagnostic rerun passed
without a fix (`artifacts/smoke-8d5cbbaf1d4d48b2b0252fea54b7ef0c`), so this is
intermittent evidence, not a reliable reproduction of the tester's Lark session.

A narrower regression was reproducible against the preserved alpha.1 binary:
`artifacts/smoke-adf3daa883bc41bfbbbf85af9f01e702` failed because the scrolling
controller permitted mouse activation and could steal source focus. The old
binary remains SHA-256
`8AED40D7C290C1492EFA53A1866B5CD3549AA002E1CBBB337FFC1EF0B37FA369`.

The fix transfers foreground to the selected source before destroying the
selection overlay, while the selection still owns foreground input rights.
The controller uses a non-activating extended style and returns MA_NOACTIVATE
for WM_MOUSEACTIVATE, preserving its mouse commands without requesting focus.
Stop/Cancel remain operational. No synthetic input is sent to user applications
by the product, and no scrolling, matching or memory thresholds were weakened.

Windows restricts foreground changes and normally routes wheel messages to the
focused window. References: [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow),
[WM_MOUSEWHEEL](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-mousewheel),
[WM_MOUSEACTIVATE](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-mouseactivate).
These explain the focus vulnerabilities; they do not prove the exact cause of
the tester's unobserved session.

### Input Probe And Desktop Preconditions

Two initial packaged full-suite attempts failed at the first scroll offset
(`smoke-183e3dad17f1429a8530bd7df7aaa496`) or foreground handoff
(`smoke-258794b464e740e88ec108e14057a3b0`). Both diagnostic logs show that the
selection itself was not foreground before teardown and activation returned
zero. The latter foreground handle belonged to AnyDesk. The test had posted a
capture command without a real launcher click, so these runs did not establish
the interactive foreground precondition. They remain recorded, not counted as
successful runs or claimed reproductions of Lark.

The harness now uses guarded SendInput clicks on its own launcher/controller
only. It verifies process ownership and the visible window under the destination,
refuses input if mouse buttons/modifiers are held, and restores the cursor only
if the user has not moved it elsewhere. It does not click user Lark/AnyDesk or
change Windows mouse settings. Direct wheel messages still exercise the source
handler and exact pixels; they are not proof of OS/hardware wheel routing.

An attempted OS-wheel probe failed even before starting scrolling capture:
`artifacts/smoke-58f3436a5a9b43a9b23b9b4f5d482ac2`. The foreground fixture did
not receive the injected wheel event. Its focusability, the desktop environment
and input delivery have not been isolated further. The optional `-InputProbe`
preserves that outside-capture preflight and in-session OS-wheel checks; a normal
ScrollChecks PASS must not be presented as an InputProbe PASS. Physical Lark
wheel input remains unverified until the tester confirms it.

A separate earlier run (`smoke-cf8b3636c05c402abef5b730741f5ade`) captured a
dimmed source pixel before scrolling tests. The harness now verifies the visible
source color before its window-capture case. This establishes a clean fixture;
it does not establish the cause of the dimming or claim a production capture
timing fix. No expected output pixel assertion was relaxed.

The guarded input check also rejected a hidden launcher in
`smoke-7dcf284993974359b04fe014610e825e`. The harness now explicitly restores
its own launcher before clicking it. A resumed run,
`smoke-aa87d59e2ce94e7e80e0ca4f3420e104`, left screenshots but no completed
results or recoverable exit status; it is not counted as a full-suite pass.

### Final Packaged Native Run

The extracted alpha.2 executable passed the full suite with `-EditorChecks
-PaintChecks -AnnotationChecks -ResizeChecks -ScrollChecks`:
`artifacts/smoke-80474e0ce2de47b798bf8e5d3630ac3b/results.json`, exit code zero.
This includes original capture pixels, editor operations, text resizing,
foreground handoff, a guarded controller click without losing source focus,
exact 240 x 653 frozen-table PNG/clipboard pixels, movement pause, Stop/Cancel,
hotkey conflict/success dialogs and clean application exit. Both tested monitors
were 96 DPI; high/mixed DPI is still a manual case.

Window-detection timings in this regression run were launcher 678.46 ms,
selection 198.8 ms and preview 23.54 ms. Peak working set was 131825664 bytes;
these are observations from the full suite, not a performance guarantee.
`scroll_os_wheel_probe` explicitly reports NOT RUN. The earlier optional
InputProbe failure remains unresolved and this PASS does not supersede it.

Portable executable: `SnapZy-Rust.exe`, 992256 bytes, product version
`0.4.0-alpha.2`, SHA-256:
`7C7709F6190C64CEAE4D2E1F801A724EEA00148E89E53E725041518D862720E0`.

## Tester Checklist

1. Save old Rust editor work and exit Rust Preview through its tray menu.
   Extract the alpha.2 ZIP to a new folder and open `SnapZy-Rust.exe`. Confirm
   the launcher shows `0.4.0-alpha.2`. No .NET runtime or installer is required.
2. Open the problematic Lark sheet, choose Scrolling and select a modest table
   region with space outside it for the controller. Include frozen header/footer
   if desired. The overlay must disappear and the table must remain interactive.
3. Place the pointer over the table and rotate the wheel downward. If necessary,
   click a cell once, then retry. Report whether clicking changes the outcome;
   do not mistake missing automatic movement for failed manual scrolling.
4. Pause between overlapping downward steps until accepted height increases.
   Stop and inspect joins. Test several times on both previously good/problematic
   sheets and on Excel or a normal page. Cancel must not open a later preview.
5. Test clicking the controller's status/title area and then scrolling over the
   table again. It must not retain input focus. Stop/Cancel must still work.
6. Recheck Area/Window/Desktop capture, text resize, drawing, PNG and clipboard.
   Try physical hotkeys, actual chat paste and 125-200%/mixed DPI separately.

Report whether the table itself moves, whether accepted height changes, whether
one click inside the table helps, the visible controller status, display scaling
and build. The automated wheel checks use real native window messages, not
physical hardware or authenticated Lark. User confirmation is still required.

### Tester Confirmation

2026-10-09: the user confirmed that manual scrolling now works. This confirms
the previously reported input-blocking symptom is resolved in their test. It
does not establish all Lark sheets, join accuracy, high DPI or the optional
automated OS-wheel probe. Automatic scrolling remains outside this pilot.

Existing limits remain: manual downward scrolling, conservative stable/overlap
checks, bounded 32 MiB aggregate source/strip capacity, no unlimited capture,
continuous-animation rejection and incomplete detection of untitled overlays.
